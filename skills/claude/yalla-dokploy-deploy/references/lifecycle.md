# Lifecycle: the canonical deploy sequence

Read this immediately before executing. Two flows: single-app and compose. Both share the same head (project + envs + domain + verify) and differ in the middle (how the workload itself is created).

Every step uses `yalla --json --no-input api call <op> --input <file>`. Capture the printed envelope per step; many ops return `{}` on success and you'll need to re-list to recover IDs.

## Common head: project + envs + (state file lookup)

### 0. Pre-flight (every run)

```sh
yalla --json auth status
```

If `ready: false`, see `references/preflight.md` and stop.

### 1. Determine the active organization

```sh
yalla --json api call user-get
```

Read `data.body.activeOrganizationId`. Use it to filter `project-all` and (if relevant) to drive future multi-org skills.

### 2. Look up or create the project

If `.dokploy.yaml` at the repo root has `project_id`, use it; verify it still exists with `project-one`:

```json
{ "query": { "projectId": ["<saved>"] } }
```

If the saved ID 404s, fall through to create.

To create:

```json
{
  "body": {
    "name": "<project_name>",
    "description": "<one-line, optional>",
    "env": ""
  }
}
```

`project-create` returns `{}`. Recover the ID via `project-all` and filter by name. Cache it locally for the rest of this run.

### 3. Make sure both environments exist

`project-create` ships a default `production` env. Add `staging` (and any others the user requested):

```sh
yalla --json api call environment-create --input <(echo '{"body":{"name":"staging","projectId":"<projectId>"}}')
```

After every `environment-create`, refetch the project to see the env IDs:

```sh
yalla --json api call project-one --input <(echo '{"query":{"projectId":["<projectId>"]}}')
```

`data.body.environments` is the canonical list. Pin the IDs:

- `prod_env_id`  → the env named `production` (or whatever the user calls prod)
- `staging_env_id` → the env named `staging`
- `target_env_id` → whichever env this run is deploying to

## Branch: single app vs compose

```
shape == "single" → go to "Single-app middle"
shape == "compose" → go to "Compose middle"
```

## Single-app middle

### 4. Look up or create the application

Inside `target_env_id`, look in the project-one response under `data.body.environments[].applications[]` for an app with the planned name. If found, skip create.

To create:

```json
{
  "body": {
    "name": "<app_name>",
    "appName": "<app_name>",
    "environmentId": "<target_env_id>",
    "description": null,
    "serverId": null
  }
}
```

`appName` is what shows in the UI. The actual swarm service name is auto-generated by Dokploy and recoverable via `application-one`.

`application-create` returns `{}`. Refetch project-one and find the new app's `applicationId`.

### 5. Save the source

Pick exactly one based on the plan (`source: git | image`). See `references/sources.md` for the full body templates. The op is one of:

- `application-saveDockerProvider`
- `application-saveGitProvider`
- `application-saveGithubProvider`
- `application-saveGitlabProvider`

Idempotent — calling again replaces the source.

### 6. Save the build type

```sh
yalla --json api call application-saveBuildType --input <body-from-build-types.md>
```

Required for any source other than `application-saveDockerProvider`. (For pre-built images, the build type still has to be set, but Dokploy ignores most of it — set `buildType: "dockerfile"` with all paths null as a safe default.)

### 7. (Optional) Provision databases

If `db_needs` is non-empty, follow `references/databases.md` per engine. The order is:

```
<engine>-create  →  recover its ID via <engine>-one or refetching project-one
<engine>-deploy
<engine>-one     →  read appName for the connection string
```

Defer the application-side wiring (step 8) until DBs are deployed — otherwise the app comes up referencing a DB that doesn't yet exist.

### 8. Save environment variables

```sh
yalla --json api call application-saveEnvironment --input <body-from-sources.md>
```

Compose the multi-line `env` string by combining:
- vars parsed from `.env*`
- the new `DATABASE_URL` (and `REDIS_URL`, etc.) from step 7

Don't forget `buildArgs`, `buildSecrets`, `createEnvFile`. See `references/sources.md`.

### 9. Create the domain

Default to `<project>-<env>.<base-host>`. The `<base-host>` should be a wildcard the user has pointed at the Dokploy server (e.g., `*.apps.example.com`).

```json
{
  "body": {
    "host": "<project>-<env>.apps.example.com",
    "path": "/",
    "port": 3000,
    "https": true,
    "applicationId": "<applicationId>",
    "certificateType": "letsencrypt",
    "customCertResolver": null,
    "composeId": null,
    "serviceName": null,
    "domainType": null,
    "previewDeploymentId": null,
    "internalPath": null,
    "stripPath": false
  }
}
```

`port` should match what the app exposes (3000 for Node defaults, 8000/8080 for Python/Go, etc.). If the project ships a Dockerfile, read its `EXPOSE`. Otherwise ask.

### 10. Deploy

```sh
yalla --json api call application-deploy --input <(echo '{"body":{"applicationId":"<id>","title":"yalla-skill: deploy","description":"<plan summary>"}}')
```

Returns immediately with `{}`. Real status comes from polling — see `references/verification.md`.

## Compose middle

### 4'. Look up or create the compose stack

```json
{
  "body": {
    "name": "<stack_name>",
    "environmentId": "<target_env_id>",
    "composeType": "docker-compose",
    "composeFile": "<paste contents of docker-compose.yml verbatim>",
    "appName": "<stack_name>",
    "description": null,
    "serverId": null
  }
}
```

`composeFile` is the **raw text** of the user's compose file. JSON-encode it (escape quotes + newlines). The skill should read the file from disk at this point.

### 5'. Save compose env

`compose-saveEnvironment` mirrors `application-saveEnvironment` shape (env / buildArgs / buildSecrets / createEnvFile). Vars apply to all services unless the compose file overrides per-service.

### 6'. Domain

Same as step 9 above, but with `composeId` instead of `applicationId`. Also fill `serviceName` to pick which compose service Traefik should route to (the one exposing the public port).

### 7'. Deploy

```sh
yalla --json api call compose-deploy --input <(echo '{"body":{"composeId":"<id>"}}')
```

## State file

After a successful deploy, write to `.dokploy.yaml` at the repo root:

```yaml
schema: yalla.dokploy.v1
project_id: <projectId>
project_name: <name>
environments:
  production: <prod_env_id>
  staging:    <staging_env_id>
applications:
  app: <applicationId>          # for single-app shape
  # OR
  compose: <composeId>          # for compose shape
domains:
  staging:    <project>-staging.apps.example.com
  production: <project>-production.apps.example.com
last_deploy:
  env: <env_name>
  at: <iso8601>
  build_type: <build_type>
```

Future runs of the skill read this and can skip everything up to step 4 / 4'.

`.dokploy.yaml` doesn't store secrets. The skill should also `.gitignore`-suggest a `.dokploy.yaml.local` for any sensitive values (DB passwords surfaced from db creation, etc.).

## Idempotency cheatsheet

| What | Idempotent? | How to retry safely |
|---|---|---|
| `project-create` | No — duplicate name fails | Look up first via `project-all` |
| `environment-create` | No — duplicate name fails | Look up first via `project-one` |
| `application-create` | No | Look up first |
| `application-save*Provider` | Yes — replace | Just re-call |
| `application-saveBuildType` | Yes | Just re-call |
| `application-saveEnvironment` | Yes — replace | Just re-call (with full env) |
| `<engine>-create` | No — duplicate name fails | Look up first via project-one |
| `<engine>-deploy` | Yes (queues a redeploy) | Re-call |
| `domain-create` | No — duplicate host fails | List existing via `domain-byApplicationId` |
| `application-deploy` | Yes — queues new build | Re-call (or use `application-redeploy`) |
| `application-redeploy` | Yes | The clean way to redeploy |
| `application-dropDeployment` | Yes — overwrites the unpacked filesystem in place | Re-call with the new zip; the previous drop is replaced. No server-side rollback, so keep your old zip on disk before re-dropping. See `references/drop-deploy.md`. |

## Drop-deploy variant

When `source == drop`, the canonical sequence is **trimmed**: there is no
source-provider step because Dokploy is not cloning anything, and the
build type still matters because the unpacked zip is the working
directory the build type reads from.

Single-app drop order:
1. `project-create` (or look up)
2. `environment-create` (or look up)
3. `application-create` — capture `applicationId`
4. `application-saveBuildType` — `"static"` if the zip is a built SPA,
   `"dockerfile"` if the zip contains a `Dockerfile` at `dropBuildPath`
5. `application-saveEnvironment` (optional but recommended pre-drop)
6. `domain-create` (optional)
7. `application-dropDeployment` — the multipart upload itself
8. Verify exactly as for any other deploy (`references/verification.md`)

Composes do not have a drop equivalent in the spec; if a user asks for a
"drop deploy" on a compose stack, that is actually a manual
`docker-compose up` against an unpacked zip and is out of scope — push
the compose source through a git provider instead.

Full recipe (input shape, `dropBuildPath` semantics, redeploy/rollback
caveats, dry-run safety) lives in `references/drop-deploy.md`.

## Failure mid-sequence

If a step fails after some resources were created:

1. Capture the partial state (project IDs, app ID if any).
2. Surface it to the user with the failed call's error envelope.
3. Offer two paths: "fix and continue" (skill will resume from the failed step) or "tear down and start over" (run `project-remove` if a project was created; the cascade kills everything inside).

Don't auto-rollback. Some errors are recoverable (E_INVALID_INPUT — the user adjusts the body and retries), and partial state is sometimes valuable (the project + envs are fine, only the app failed).

## Worked example: minimal Node app, single-env, no DB

```sh
PROJ=$(uuidgen)  # dummy, real id comes from project-all after create

# 1. Project
yalla --json --no-input api call project-create --input <(echo '{"body":{"name":"my-app","description":"E2E test","env":""}}')
PROJ_ID=$(yalla --json api call project-all | jq -r '.data.body[] | select(.name=="my-app") | .projectId')

# 2. Staging env
yalla --json --no-input api call environment-create --input <(echo "{\"body\":{\"name\":\"staging\",\"projectId\":\"$PROJ_ID\"}}")
ENV_ID=$(yalla --json api call project-one --input <(echo "{\"query\":{\"projectId\":[\"$PROJ_ID\"]}}") | jq -r '.data.body.environments[] | select(.name=="staging") | .environmentId')

# 3. Application
yalla --json --no-input api call application-create --input <(echo "{\"body\":{\"name\":\"my-app\",\"environmentId\":\"$ENV_ID\"}}")
APP_ID=$(yalla --json api call project-one --input <(echo "{\"query\":{\"projectId\":[\"$PROJ_ID\"]}}") | jq -r '.data.body.environments[] | select(.environmentId=="'$ENV_ID'") | .applications[] | select(.name=="my-app") | .applicationId')

# 4. Source: generic git
yalla --json --no-input api call application-saveGitProvider --input <(echo "{\"body\":{\"applicationId\":\"$APP_ID\",\"customGitUrl\":\"https://github.com/owner/repo.git\",\"customGitBranch\":\"main\",\"customGitBuildPath\":\"/\",\"watchPaths\":[],\"customGitSSHKeyId\":null,\"enableSubmodules\":false}}")

# 5. Build type: nixpacks
yalla --json --no-input api call application-saveBuildType --input <(echo "{\"body\":{\"applicationId\":\"$APP_ID\",\"buildType\":\"nixpacks\",\"dockerfile\":null,\"dockerContextPath\":null,\"dockerBuildStage\":null,\"herokuVersion\":null,\"railpackVersion\":null,\"publishDirectory\":null,\"isStaticSpa\":null}}")

# 6. Env vars
yalla --json --no-input api call application-saveEnvironment --input <(echo "{\"body\":{\"applicationId\":\"$APP_ID\",\"env\":\"NODE_ENV=production\\nPORT=3000\\n\",\"buildArgs\":\"\",\"buildSecrets\":\"\",\"createEnvFile\":true}}")

# 7. Domain
yalla --json --no-input api call domain-create --input <(echo "{\"body\":{\"host\":\"my-app-staging.apps.example.com\",\"path\":\"/\",\"port\":3000,\"https\":true,\"applicationId\":\"$APP_ID\",\"certificateType\":\"letsencrypt\",\"customCertResolver\":null,\"composeId\":null,\"serviceName\":null,\"domainType\":null,\"previewDeploymentId\":null,\"internalPath\":null,\"stripPath\":false}}")

# 8. Deploy
yalla --json --no-input api call application-deploy --input <(echo "{\"body\":{\"applicationId\":\"$APP_ID\",\"title\":\"yalla-skill: initial deploy\"}}")

# 9. Verify (loop)
# see references/verification.md
```
